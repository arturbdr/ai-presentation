The point of this talk: a prompt helps one session, a committed rules file helps every session for every developer. First WHY: what goes wrong without rules. Then HOW: a real service, built up one file at a time.
chapter 1 · the duel

One developer. One AI.

It's fast, it's confident, and it has no idea how your team builds software.

Tell this as a story. Meet Duke: that's us, the developers, with our codebase and our conventions.
First duel: one developer, one AI assistant. It writes code quickly and sounds sure of itself, but it has never seen our architecture, our test stack or our standards.
Point at the stone on the right: "Better AI together? ...or not." That's the question for this talk.
the problem

Without rules, your AI guesses

01

No memory between sessions

Each conversation starts from zero. The same instructions get repeated every session.

02

Generic defaults

Package layout, DTOs, and boilerplate that do not match how this codebase is structured.

03

Skipped verification

Code changes land without a build, a test run, or a lint pass.

04

Inconsistent answers

Two developers asking the same question get two different results.

WHY, part one. Each card is a failure you have probably seen already. Keep these four in mind, because the last slide maps every one of them to a fix.
- No memory: you re-explain the stack every session.
- Generic defaults: the model writes the average Spring app, not ours.
- Skipped verification: "done" without running anything.
- Inconsistent answers: two developers, two different styles.
chapter 2 · a new challenger

New tool. Same fight.

Switch assistants and you start from zero. Nothing you explained yesterday carries over.

Problem card 01, no memory. Another tool, or just a new session with the same tool, and the fight starts over.
Everything you explained in yesterday's prompt is gone. You re-explain the stack, the layering, the test rules, every time.
chapter 3 · double trouble

Two assistants. Two sets of defaults.

Same question, two different answers, and your conventions in neither of them.

Problem cards 02 and 04: generic defaults and inconsistent answers.
Half the team uses one assistant, half uses another. Each one falls back on its own idea of a "typical" Spring app. Two developers ask the same question and get two different designs, and neither matches ours.
chapter 4 · outnumbered

Every tool. Every session. Guessing.

Repeating the rules in every prompt doesn't scale. Something has to change.

Problem card 03 and the sum of all four. Three tools, a whole team, dozens of sessions a day, and nobody runs the build before saying "done".
Pause here. Ask the room: who has re-explained the same convention to an AI this week?
Then: let's look at the service we're defending.

chapter 5 · the shield

Write the rules down. Once.

In the repo, reviewed like code, loaded by every session. The shield is made of rule files.

The turn in the story. Duke stops fighting each blast by hand and raises a shield, and the shield is made of rule files. Kodee, the Kotlin mascot, joins in: our stack's conventions are part of the shield.
Point at the crate: .claude/rules/. That's the whole idea of this talk. Instead of repeating ourselves in prompts, we write each decision down once, and every session loads it.
The file names on the shield are illustrative. Next: how the files actually work, then what goes in ours.
how it works

Project memory, loaded automatically

CLAUDE.md

  • Root-level Markdown file
  • Loaded in full at the start of every session
  • Project, user, or managed-org scope
  • Recursed from the working directory up to the repo root

.claude/rules/*.md

  • One file per topic: testing.md, architecture.md, and so on
  • Can be scoped to specific file types or paths
  • Loaded automatically, no import needed; path-scoped files load only when matching files are touched
  • Keeps the root file short as the project grows

Both are committed to the repo and reviewed like code. The whole team works from the same rules, not just whoever wrote the last prompt.

HOW, the mechanics. CLAUDE.md loads in full every session, so every line costs context. Files in .claude/rules/ are picked up automatically, with no import needed. A rule file with paths: frontmatter loads only when Claude works on matching files. Both are committed and reviewed like code. That's the whole mechanism.

What actually goes in CLAUDE.md

CLAUDE.md · project root
# CLAUDE.md

## Communication
- Expert-level audience. Skip basic explanations.

## Guardrails
- Before editing, read the files you will change and
  their tests.
- Never assume unfamiliar code, libraries, or framework
  behavior — verify by reading the code first.
- When in doubt, stop and ask. Do not guess.

## Non-negotiables
- A change that breaks `clean-code.md` is not done,
  tests included.
- Never swallow an exception: rethrow, translate, or
  handle it.
- Never log secrets, tokens, or personal data. Log ids.

## Stack
- Kotlin 2.2, Spring Boot 4, Maven
- Persistence: Spring Data JDBC, PostgreSQL
- Tests: JUnit 5, MockK, Testcontainers for integration tests

Principle: CLAUDE.md holds only what Claude can't guess.
- Communication: sets the level of detail.
- Guardrails: concrete, checkable behaviors ("read the files first", "stop and ask"), not vague ones like a confidence percentage the model can't measure.
- Non-negotiables: three lines, on purpose. Clean code, never swallowing exceptions, never logging personal data. They're in context from the first message of every session. The details stay in clean-code.md, error-handling.md and observability.md, which is the pattern: the root file states the non-negotiable, and the rule file explains it. Nothing is copied, so nothing drifts.
- Stack: exact versions, so it doesn't guess Mockito or H2.

# Testing rules

## Frameworks
- JUnit 5 + MockK. Never introduce Mockito.
- Testcontainers for anything touching Postgres. No H2:
  it hides Postgres-only behavior that breaks in prod.

## Structure
- One behavior per test. The name states the behavior,
  not the method under test.
- Always structure the body with // given, // when,
  // then comments, in that order. No other comments.
- Build test data with builders, not inline object
  literals.

## Assertions
- Use AssertJ fluent assertions: assertThat(result)
  .isEqualTo(...). Never JUnit's assertEquals/assertTrue.
- Chain related checks on one assertThat(...) instead of
  repeating it per field.

## Coverage
- Every new usecase ships a test for at least one failure path.
- Controller tests use @WebMvcTest, not full @SpringBootTest.

# Architecture rules

## Layering
- domain/              entities, value objects, business
                        rules. Zero framework imports.
- usecase/             application logic. Depends on
                        domain only.
- gateway/
  ├── controller/      inbound HTTP adapters. Depend on
  │                    usecase.
  └── jdbc/            outbound persistence adapters.
                        Implement a port interface owned
                        by usecase.

## Boundaries
- gateway/controller and gateway/jdbc never depend on each other.
- New persistence code goes in gateway/jdbc, never in domain
  or usecase.

Rule: clean code, every change

.claude/rules/clean-code.md · no paths: loads every session
# Clean code rules
Applies to every change: production code and tests.

## Functions
- At most 20 lines and 4 parameters. Beyond that, split
  the function or introduce a parameter object.
- Guard clauses over nested if/else. Nesting depth 2 max.
- Getters and query methods never change state: callers
  rely on reads being safe to repeat.

## Naming
- No generic suffixes: Manager, Helper, Util, Data, Info.
  They hide what the class actually does.
- No abbreviations: campaignRepository, not campRepo.
- No magic numbers or strings. Extract a named constant.

## Classes
- usecase/ depends on ports, never on gateway/ classes.
- No abstract base classes just to share code. Extract a
  function or a collaborator instead.

## Hygiene
- Logic that appears twice is extracted, not copied.
- No comments unless asked. Exception: // given/when/then
  in tests. Names explain the code, comments don't.
- No commented-out code. No TODO without a ticket id.
- Clean up code you touch, but never refactor unrelated
  code in the same change: it makes the diff unreviewable.

- detekt enforces the numeric limits above in the build.
- Never add @Suppress to get past a detekt finding.

Rule: Kotlin conventions

.claude/rules/kotlin.md
# Kotlin conventions

## Language idioms
- Model state with data classes; model alternatives with
  sealed classes/interfaces, not enums with fields.
- Extension functions for behavior that reads naturally
  on the receiver. Do not overuse: a member fits a class's
  own concern, an extension fits a cross-cutting one.
- Prefer immutability: val over var, immutable collections
  over mutable ones.

## Calls
- Named arguments on any call with more than two
  parameters, or where types alone don't disambiguate
  meaning (e.g. two Boolean or String parameters in a row).

# Error handling rules

## Domain exceptions
- Every business error has its own exception: a subclass of
  the sealed CampaignException in domain/. Named after the
  business meaning, never after an HTTP status.
- domain/ never throws Spring or JDBC types.
- require(...) / check(...) only guard internal invariants.
  A failure there is a bug, so it becomes a 500.

## Translation at the edge
- gateway/jdbc translates only the database errors a use
  case reacts to: DuplicateKeyException becomes
  CampaignAlreadyExistsException.
- No SQL or JDBC type ever leaves gateway/.

Error handling is a decision Claude can't infer: Kotlin and Spring allow exceptions, Result, sealed types, try/catch per controller or one central handler. Without this file, every session picks a different one. Team decision: sealed exceptions.

- require/check are for bugs, not business rules. A business rule that fails gets its own exception, like InvalidCampaignPeriodException.
- gateway/jdbc translates only what a use case reacts to. Everything else propagates and becomes a 500.

Rule: error handling (cont.)

.claude/rules/error-handling.md
## HTTP mapping
- One @RestControllerAdvice maps exceptions to ProblemDetail
  (RFC 9457). Controllers never try/catch.
- CampaignException is mapped with an exhaustive when and
  no else branch: a new exception without a status fails
  to compile.

  CampaignNotFoundException          → 404
  CampaignAlreadyExistsException     → 409
  CampaignAlreadyCancelledException  → 409
  InvalidCampaignPeriodException     → 400
  request DTO validation (@Valid)    → 400
  anything else                      → 500, no internals

## Never
- catch Exception or Throwable outside the advice.
- Swallow an exception: rethrow, translate, or handle it.
- runCatching in production code: it catches Throwable.

- The key trick: CampaignException is sealed and the advice uses an exhaustive when with no else. Add a new exception without a status and the build fails. The compiler enforces the mapping, not the model's memory.
- Every status comes from a dedicated exception, except two cases on purpose. @Valid failures on the request DTO are an HTTP concern, so they map to 400 directly. Anything unexpected is a 500 with no internals in the body.
- Logging of these exceptions is defined in observability.md (next slide): 5xx at ERROR with stack trace, 4xx at WARN without.
- "Never" section: each item has its reason or alternative. runCatching catches Throwable, which hides real bugs.

# Observability rules

## Where to log
- usecase/: one INFO line per completed business action.
- gateway/: calls to external systems at DEBUG; failures
  at WARN with the target and the duration.
- Exceptions are logged once, by the @RestControllerAdvice:
  5xx at ERROR with stack trace, 4xx at WARN without.
  Alerts fire on ERROR only.
  Never log and rethrow.
- domain/: no logging. It has zero framework imports.

## What to log
- Key-value pairs, not string concatenation:
  log.atInfo().addKeyValue("campaignId", id).log("Campaign created")
- Never log secrets, tokens, or personal data (email,
  name, phone). Log ids instead: logs are kept for months.

## Metrics and tracing
- Business counters via Micrometer: campaigns.created.
  Low-cardinality tags only, never ids.
- Trace ids come from Micrometer Tracing. Never create or
  pass them by hand.

Rule: verify before you're done

# Verification rules

## After every change, always
1. mvn test              run the unit tests
2. mvn verify -Pit       run the integration tests
3. mvn spotless:check    lint the code (ktlint via Spotless)
4. mvn detekt:check      clean-code limits (size, nesting)

## Rules
- Do not report a task finished if any command fails.
- If a command is missing or errors out, stop and ask.
  Do not guess.
- Never suppress a linter warning just to make it pass.
- Before reporting done, re-read the diff against
  clean-code.md and fix every violation.
- Dead code check: scan for unused imports, functions,
  classes, and parameters after every change. Remove them.
- Never run git add, git commit, or git push.

## Refactoring
- A refactor never changes behavior. If output changes,
  it is a rewrite, not a refactor.
- Before refactoring, check for a test that covers the
  code. None exists? Write it first, then refactor.

code quality

Will the AI actually write clean code?

Not because we asked nicely. Four layers, each catching what the one before it missed:

1

The rule. clean-code.md loads in every session. Its limits are numbers, not adjectives, so Claude writes to the standard from the first line.

2

Self-review. verification.md makes Claude re-read its own diff against clean-code.md and fix every violation before it reports "done".

3

The build and a hook. detekt and ktlint fail on violations, and suppressing them is banned. A Stop hook can run them automatically and block Claude from finishing until they pass.

4

The PR. CI runs the same checks, and a human reviews AI code against the same clean-code bar as anyone else's.

A written rule shapes the code; tools and review verify it. When something slips through, it becomes a sharper rule or a stricter detekt threshold.

This slide is for the question "how do we know the AI will follow clean code?"
Be honest: a rule in a Markdown file is strong guidance, not a guarantee. The model follows specific, checkable rules far more reliably than vague ones, but nobody should rely on the rule alone.
That's why there are four layers:
1. The rule sets the target on every session.
2. Self-review catches most slips before a human sees them.
3. detekt and ktlint are deterministic. They don't depend on the model's judgment at all. Anthropic's docs are explicit: CLAUDE.md is "context, not enforced configuration"; hooks "are deterministic and guarantee the action happens". A Stop hook that runs detekt is the hard guarantee.
4. PR review and CI: AI code gets exactly the same bar as human code.
And the loop: every slip that reaches review becomes a sharper rule or a stricter threshold, so quality goes up over time.

how to write them

Writing rules: do and don't

Do

  • Write rules concrete enough to verify: "run mvn test", not "test your changes".
  • Keep each file under 200 lines. Longer files reduce adherence.
  • Use headers and bullets. Claude scans structure like a reader does.
  • Explain the why when it isn't obvious. Claude generalizes from the reason.
  • Pair every ban with the alternative: "MockK, never Mockito".
  • Scope topic rules with paths: so they load only when relevant.
  • Test a rule: change it, then check that Claude's behavior actually changes.

Don't

  • State the self-evident: "write clean code", "follow SOLID". Claude knows.
  • Describe what Claude can read in the code: file tours, API docs. Link instead.
  • Include information that changes often. It goes stale and misleads.
  • Let two rules contradict each other. Claude may follow either one.
  • Shout. Use IMPORTANT on one line at most; if everything is important, nothing is.
  • Rely on a rule for what must never fail. Use a hook or a build check.
  • Let it grow unreviewed. If Claude already does it right, delete the line.
sources: code.claude.com/docs/en/best-practices · code.claude.com/docs/en/memory
This is the checklist for anyone writing or reviewing a rule file. Every line comes from Anthropic's own docs, not from opinion.
Do:
- "Write instructions that are concrete enough to verify" (memory docs).
- "Target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."
- Headers and bullets: "organized sections are easier to follow than dense paragraphs".
- The why: the prompting guide says explaining why "can help Claude better understand your goals", and "Claude is smart enough to generalize from the explanation".
- Test it: "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts."

how to write them

Should rules include code examples?

✓

Yes: short, inline

A one-line right-vs-wrong example beats a description. Anthropic calls examples "one of the most reliable ways to steer" Claude's output.

✓

Better: point to a real file

"New use cases follow usecase/CreateCampaign.kt." Always up to date, reviewed, and costs nothing until Claude opens it.

✗

Avoid: pasted classes

A full code block loads every session, goes stale, and gets copied closely, mistakes included. If you really need a template, use a path-scoped rule or a skill.

.claude/rules/architecture.md · the recommended form
## Reference implementations
- New use cases follow usecase/CreateCampaign.kt.
- New persistence adapters follow gateway/jdbc/CampaignJdbcRepository.kt.
sources: code.claude.com/docs/en/best-practices ("Reference existing patterns") · platform.claude.com prompting best practices ("Use examples effectively")
Short answer: yes to examples, no to pasted code.
- Anthropic's prompting guide: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure." It also warns to vary them "enough that Claude doesn't pick up unintended patterns". Claude copies examples closely, so a flawed example spreads.
- Claude Code best practices, "Reference existing patterns": point Claude to a pattern in your codebase ("HotDogWidget.php is a good example") instead of describing it.
- The same page lists "Anything Claude can figure out by reading code" and "Long explanations or tutorials" under Exclude, and says to use skills for knowledge "only relevant sometimes", because they load on demand.
So: one-line do/don't examples inline (our api.md does this), a pointer to a reference file for bigger patterns, and never a pasted class in CLAUDE.md. The docs don't forbid code blocks in rules, but these three habits follow from their guidance.
Important: the reference file must itself be clean code. Claude will copy whatever it finds there.
