the problem

Without rules, your AI guesses

01

No memory between sessions

Each conversation starts from zero. The same instructions get repeated every session.

02

Generic defaults

Package layout, DTOs, and boilerplate that do not match how this codebase is structured.

03

Skipped verification

Code changes land without a build, a test run, or a lint pass.

04

Inconsistent answers

Two developers asking the same question get two different results.

how it works

Project memory, loaded automatically

CLAUDE.md

  • Root-level Markdown file
  • Loaded in full at the start of every session
  • Project, user, or managed-org scope
  • Recursed from the working directory up to the repo root

.claude/rules/*.md

  • One file per topic: testing.md, architecture.md, and so on
  • Can be scoped to specific file types or paths
  • Loaded alongside CLAUDE.md, same session
  • Keeps the root file short as the project grows

Both are committed to the repo and reviewed like code. The whole team works from the same rules, not just whoever wrote the last prompt.

Rule: testing guidelines

.claude/rules/testing.md
# Testing rules

## Frameworks
- JUnit 5 + MockK. Never introduce Mockito.
- Testcontainers for anything touching Postgres. No H2.

## Structure
- One behavior per test. The name states the behavior,
  not the method under test.
- Always structure the body with // given, // when,
  // then comments, in that order. No other inline
  comments.
- Build test data with builders, not inline object
  literals.

## Assertions
- Use AssertJ fluent assertions: assertThat(result)
  .isEqualTo(...). Never JUnit's assertEquals/assertTrue.
- Chain related checks on one assertThat(...) instead of
  repeating it per field.

## Coverage
- Every new usecase ships a test for at least one failure path.
- Controller tests use @WebMvcTest, not full @SpringBootTest.

Rule: architecture guidelines

.claude/rules/architecture.md
# Architecture rules

## Layering
- domain/              entities, value objects, business
                        rules. Zero framework imports.
- usecase/             application logic. Depends on
                        domain only.
- gateway/
  ├── controller/      inbound HTTP adapters. Depend on
  │                    usecase.
  └── jdbc/            outbound persistence adapters.
                        Implement a port interface owned
                        by usecase.

## Boundaries
- gateway/controller and gateway/jdbc never depend on each other.
- New persistence code goes in gateway/jdbc, never in domain
  or usecase.

Rule: architecture guidelines (cont.)

.claude/rules/architecture.md
## Naming
- Use cases are verbs: CreateCampaign, CancelCampaign.
- Ports are nouns with a Port suffix: CampaignRepositoryPort.

## Clean Code
- Small, single-purpose functions; one level of
  abstraction each.
- Intention-revealing names; no abbreviations or magic
  values.
- No hidden side effects behind getters or "query" methods.
- Guard clauses over nested if/else.
- Follow SOLID; one reason to change per class or function.
- No comments unless asked. Exception: // given/when/then
  in tests.

Rule: Kotlin conventions

.claude/rules/kotlin.md
# Kotlin conventions

## Language idioms
- Model state with data classes; model alternatives with
  sealed classes/interfaces, not enums with fields.
- Extension functions for behavior that reads naturally
  on the receiver. Do not overuse: a member fits a class's
  own concern, an extension fits a cross-cutting one.
- Prefer immutability: val over var, immutable collections
  over mutable ones.

## Calls
- Named arguments on any call with more than two
  parameters, or where types alone don't disambiguate
  meaning (e.g. two Boolean or String parameters in a row).

Rule: API & controller guidelines

.claude/rules/api.md
# API rules

## Controllers
- Every endpoint is documented (KDoc) and exposed via
  OpenAPI (see below).
- Secured with Spring Security + JWT by default. Public
  routes must opt out explicitly, e.g. @PublicEndpoint.

## URI conventions
- Resource nouns, plural: /campaigns, /campaigns/{id}.
- No verbs in the path: /campaigns/{id}/cancel, never
  /cancelCampaign.
- Nest one level at most: /campaigns/{id}/items.

Rule: API & controller guidelines (cont.)

.claude/rules/api.md
## OpenAPI / Swagger
- Every controller carries @Tag; every endpoint carries
  @Operation and an @ApiResponse per status code.
- Swagger UI must build with zero missing-schema warnings.

## Request/Response DTOs
- Never expose domain or entity types on a controller.
- One DTO for the request, one for the response body.
  Never reuse a DTO for both directions.
- Every field has @Schema(description = "..."). No
  undocumented fields in Swagger.

Rule: verify before you're done

.claude/rules/verification.md
# Verification rules

## After every change, always
1. mvn test              run the unit tests
2. mvn verify -Pit       run the integration tests
3. mvn spotless:check    lint the code (ktlint via Spotless)

## Rules
- Do not report a task finished if any command fails.
- If a command is missing or errors out, stop and ask.
  Do not guess.
- Never suppress a linter warning just to make it pass.
- Dead code check: scan for unused imports, functions,
  classes, and parameters after every change. Remove them.
- Never run git add, git commit, or git push.

## Refactoring
- A refactor never changes behavior. If output changes,
  it is a rewrite, not a refactor.
- Before refactoring, check for a test that covers the
  code. None exists? Write it first, then refactor.

next steps

Getting started

1

Start with one CLAUDE.md at the project root: stack, layering rules, the two commands to run after a change.

2

Split into .claude/rules/*.md files as the root file grows past a few topics.

3

Commit both. Review changes to rules the same way you review changes to code.

4

A rule that gets ignored needs to be more specific, not repeated louder.

why it matters

Why bother with rules at all?

  • Fewer hallucinated conventions. Claude answers from the rule instead of guessing how your team does things.
  • Consistent, team-decided behavior. Every session follows the same conventions, not whoever wrote the last prompt.
  • Easier for outside contributors. A new teammate, or another team opening a PR, follows the same file everyone else does.
  • Less spent rediscovering the codebase. No re-exploring it each session to infer conventions that are already written down.
  • Faster ramp-up, human or AI. Reading one CLAUDE.md beats reverse-engineering a project from scratch.
  • Reviewable like code. Rules live in git and get diffed and reviewed, instead of decaying in a Slack thread.

Each of these maps back to a problem from the start of this talk: no memory, generic defaults, skipped verification, inconsistent answers.

A few equivalents out there

  • Cursor — own format, .cursor/rules/*.mdc. Reads AGENTS.md too, not CLAUDE.md.
  • GitHub Copilot — .github/copilot-instructions.md, plus path-scoped .github/instructions/*.md
  • Windsurf — .windsurfrules
  • AGENTS.md — the open convention. As of Sept 2026, Claude Code, Cursor, and Copilot's coding agent all read it.

The file name changes. The idea — write the decision down once, let every session and every tool read it — doesn't.

practical

Getting GitHub Copilot to read this

1

Copilot's coding agent already reads CLAUDE.md directly, alongside its own formats. If that's the product in use, there's nothing to convert.

2

For the one-file-per-topic split, mirror each .claude/rules/*.md into .github/instructions/*.instructions.md with an applyTo glob.

3

For the lowest common denominator across every tool, add a root AGENTS.md.

.github/instructions/testing.instructions.md
---
applyTo: "src/test/**"
---

# Testing rules
(same content as .claude/rules/testing.md)

Confirmed for GitHub's Copilot coding agent as of 2026. Copilot Chat in VS Code has its own, separate AGENTS.md support, which was opt-in at last check — verify before relying on it.
